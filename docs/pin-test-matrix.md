# 贴图（Pin）场景测试清单

把「用的时候一个一个发现」换成可重跑的清单：`Baton --pin-suite` 按本表逐条跑
**真窗口 + 真鼠标事件**，输出 `PASS / FAIL`，退出码非 0 表示有用例挂了。

## 怎么跑

```bash
./Scripts/make-app.sh debug
./dist/Baton.app/Contents/MacOS/Baton --pin-suite; echo "exit=$?"
cat /tmp/baton-pin-suite.log
```

- 需要「辅助功能」权限（投递 CGEvent）。跑的时候会真的挪鼠标、开关窗口，别在演示中途跑。
- 用的是临时库 `$TMPDIR/baton-pin-suite-store`，不碰真实贴图记录。

## 三层验证，各管一段

| 层 | 管什么 | 在哪 |
|---|---|---|
| 单测 | 纯逻辑：键位映射、几何换算、撤销栈、图片解码 | `swift test`（309 条） |
| 实机场景 | 事件到底送到谁、私有状态有没有跟着变 | `--pin-suite`（28 条） |
| 人工 | 会弹模态框、需要人眼判断的 | 下表标「人工」 |

实机场景是补单测的盲区：光标不换、拖拽搬窗口、空格没反应，这些问题都不是「算错了」，
而是 AppKit 把事件送到了别处，单测调用自己的方法天然绕过那一层。

## 一个已知的测量限制

`NSCursor.current` 在后台进程里不一定跟着变：把「只读态返回箭头」的守卫删掉，
系统光标照样是箭头，用例不会红。所以 P15 断言的是画布自己的判定
（`cursorIsArrow`），真实光标形状由单测 `PinCanvasInteractivityTests` 守着。
要验真机光标只能人眼看一眼。

## 反向验证记录

证明这些断言不是摆设——把实现改回旧写法，看对应用例会不会红。

| 临时改动 | 结果 |

| 画布 `hitTest` 恒返回 `nil`（事件不归画布） | P06 / P06b / P07 / P08 / P09 / P10 / P12 / P13 共 8 条红 |
